# Приватные онлайн-комнаты

## Почему не Postgres и не Supabase Realtime

Supabase Realtime подходит для Presence и редких событий лобби, если включены
private channels и RLS. Для этого этапа он не нужен: создание комнаты,
готовность и бой обслуживаются одним match-server.

Postgres не получает кадровые input/state-сообщения. Это исключает лишние
записи, задержку logical replication и зависимость боя от квот базы.

## Сетевой поток

1. Фронтенд создаёт комнату через `POST /rooms`.
2. Сервер возвращает код, `matchId`, слот и 256-битный reconnect-токен.
3. Друг открывает `/online/CODE` и занимает второй слот.
4. Оба клиента подключаются к `/ws` и выбирают персонажей.
5. После готовности сервер запускает `CombatSimulation` на 60 Гц.
6. Клиент отправляет только битовый ввод; snapshot приходит каждые 3 тика.
7. Клиент предсказывает свой ввод, сверяется со snapshot и интерполирует друга.

Rollback пока не используется.

## Локальный запуск

В двух терминалах:

```bash
npm run match:dev
npm run dev
```

Откройте `http://localhost:5173/online`.

## Бесплатный тестовый деплой

В репозитории есть `render.yaml` для бесплатного Render Web Service. При
создании Blueprint укажите в `CLIENT_ORIGINS` точный HTTPS-адрес фронтенда.
После деплоя добавьте в Vercel:

```text
VITE_MATCH_SERVER_URL=https://ИМЯ-СЕРВИСА.onrender.com
```

Затем пересоберите фронтенд. Бесплатный Render может засыпать после 15 минут
без входящего HTTP/WebSocket-трафика, поэтому первая комната после простоя
может открываться около минуты.

## Production

Match-сервер должен работать в одном экземпляре, потому что комнаты находятся
в памяти. Перед горизонтальным масштабированием нужно добавить shared
in-memory transport или sticky routing. Игровые кадры всё равно не следует
переносить в обычную SQL-таблицу.
